# 技术可行性与选型报告

> 文档角色：当前技术选择、代价、风险与切换条件
> 权威级别：L1（技术决策依据）
> 状态：已生效
> 适用范围：一期 Go 服务与本地/测试环境
> 事实来源：当前依赖、代码结构、Docker Compose、测试与性能记录
> 最后更新：2026-08-31

## 1. 目标与约束

项目目标是在单机环境完成可运行、可测试、可讲清楚的游戏业务后台闭环。优先级依次为业务正确性、数据边界、可验证性和学习成本，不以商业级容量或分布式复杂度为目标。

当前约束：个人学习项目、单 Go 进程、Docker MySQL/Redis、本地接口客户端；没有云资源、SRE 团队、生产流量或多实例一致性要求。

## 2. 选型结论

| 领域 | 当前选择 | 主要理由 | 当前代价 |
| --- | --- | --- | --- |
| HTTP | Gin | 路由、中间件与 JSON 处理直接，项目已有实现 | 框架层不提供完整业务分层 |
| 数据访问 | `database/sql` + MySQL Driver | SQL 和事务边界透明，便于学习锁、索引和幂等 | 手写扫描与查询代码较多 |
| 主数据库 | MySQL 8.4 | 关系事务、唯一约束、索引和目标岗位匹配 | 本地凭据与 schema 需自行维护 |
| 实时状态 | Redis 7 | TTL、Hash、ZSet 和 Lua 适合在线、匹配与排行投影 | 与 MySQL 不具备跨存储事务 |
| 长连接 | Gorilla WebSocket + JSON | 浏览器/工具兼容，消息可读，便于调试 | 编码体积和解析成本高于二进制协议 |
| 部署形态 | 模块化单体 | 链路短、启动简单、故障定位直接 | 内存状态不支持多实例共享或重启恢复 |
| 本地依赖 | Docker Compose | 固定 MySQL/Redis 版本并便于清理 | Go 服务仍需在宿主机启动 |

## 3. 方案对比

### Gin 与 Echo

两者都能满足当前 REST API。项目已经围绕 Gin 建立路由、中间件和测试，迁移到 Echo 不产生业务收益。只有当团队标准、现有中间件生态或统一工程模板明确要求时才评估迁移。

### `database/sql` 与 ORM

当前结算需要唯一约束、显式事务、`SELECT ... FOR UPDATE` 和固定锁顺序，手写 SQL 更容易审查。若未来 CRUD 模型数量显著增长且团队已有成熟 ORM 规范，可在不隐藏关键事务的前提下局部引入；资产和结算核心仍应保留可审查 SQL。

### MySQL 与 PostgreSQL

两者都能满足当前规模。MySQL 是当前运行事实；PostgreSQL 仅是早期学习历史。只有出现 PostgreSQL 专有能力、组织基础设施要求或明确迁移收益时才重新评估，不能仅凭流行度反复切换。

### WebSocket JSON 与自定义 TCP/Protobuf

JSON WebSocket适合当前客户端工具、小队、任务会话和控制消息。当前没有逐帧模拟、极低延迟或高带宽证据，因此不需要自定义 TCP、UDP/KCP 或二进制协议。若后续测量证明 JSON 编解码或包体成为瓶颈，应先建立兼容测试和性能基线，再做独立协议实验。

### 单体与微服务

当前模块间调用位于同一进程，数据和故障边界尚未形成拆分压力。微服务会立即引入服务发现、RPC、配置、部署、追踪和分布式事务成本。只有出现独立扩缩容、团队所有权、发布节奏、故障隔离或容量差异的真实证据时，才依据模块边界拆分。

### Redis 与消息队列

Redis 当前承担在线 TTL、匹配 ticket 和排行榜投影，不承担可靠异步事件总线。项目没有跨服务异步消费需求，因此不引入 MQ。若未来需要可靠重试、事件回放、多个独立消费者或削峰，应先定义消息所有权、幂等和失败补偿，再选择一种 MQ 做独立验证。

## 4. 成本与风险

| 风险 | 当前影响 | 控制方式 | 触发升级条件 |
| --- | --- | --- | --- |
| 内存小队/任务丢失 | 服务重启后会话清空 | 明确学习环境边界，不承诺恢复 | 需要重启恢复或多实例时设计持久化/共享状态 |
| MySQL 与 Redis 最终一致 | 排行投影同步失败时可能落后 | MySQL 先提交；幂等重试可修复投影 | 需要自动恢复时引入重建任务或 Outbox |
| 单进程故障 | 服务不可用 | 本地重启与健康检查 | 有可用性目标时增加容器化服务与编排 |
| Query token | WebSocket URL 可能经过客户端历史/代理 | 访问日志仅记录 path，文档要求脱敏 | 公开部署前改为更安全的握手鉴权方案 |
| 开发默认 Secret | 不适合公开环境 | 环境变量覆盖，部署文档明确禁止沿用 | 任何公网或共享测试环境 |
| 缺少登录限流 | 可被暴力尝试 | 当前记录为已知风险 | 对外开放前必须实现并测试 |

## 5. 可行性结论

当前技术栈足以支撑一期单实例业务闭环和本地工程证据。它不证明生产容量、云原生能力、商业级战斗同步或微服务经验。后续升级必须由需求、故障或可复现测量触发，而不是仅为增加技术名词。
